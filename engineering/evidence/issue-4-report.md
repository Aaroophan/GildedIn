## Implemented and locally covered

The project now uses the established Auth.js provider interfaces for Google OIDC and GitHub OAuth, with server validation of stable subjects and strict separation of account IDs from any email address. The Auth.js handshake is a short-lived, non-authoritative verification step: a same-origin CSRF/HMAC-verified one-time exchange creates a server-revocable opaque application session with a hashed verifier. Session status, idle/absolute expiry, persisted security generation, provider ownership and account status are checked at every protected server entry. All state-changing owner APIs verify exact apex origin and server-side session-bound CSRF.

A current owner can read an allowlisted private profile, update only display name, obtain a new CSRF proof, list provider labels, create a short-lived provider-link intent, complete an Auth.js-verified link, unlink safely, revoke the active session or revoke all. A minimal login/finish screen, protected dashboard and linking screen are included. Provider linking is bound to the same session, account, provider and one-time nonce; after success its security generation is incremented. Unlink requires recent authentication using a provider that will remain, and prevents concurrent elimination of all sign-in methods. Administrator bootstrap is a trusted offline operation that checks a stable provider subject, reviewed approval and writes an audited role change in one transaction.

The expanded synthetic tests exercise stable-subject collisions, identical emails across Google/GitHub accounts, GitHub without verified email, hostile subject/issuer claims, repeated JWT exchanges, concurrent exchanges, non-usable sessions and TTL lag, failed audit rollback, CSRF token rotation and cross-session refusal, link-intent theft/expiry/mismatch, concurrent unlink, last-provider safety, stale recent authentication, suspended-account denial, profile role mass assignment and admin bootstrap replay. The tests also preserve all previous persistence, privacy and release/slug/tenant security checks. **Only the fake driver executes these tests**; they are not live MongoDB or provider proofs.

## Blockers that prevent release or closure

1. **Dependency and build:** The original uploaded ZIP lacked the official `mongodb` driver and the `next-auth` package. Network access to npm was unavailable in this environment, so neither package was installed or inserted as unverified entries in the existing package lock. The new Auth.js integration therefore **does not build/run from `npm ci` in this artifact**. `npm run deps:identity` is provided to install reviewed candidate versions on a connected machine, update lockfile and require an actual Next.js 16 build/test review. CI is expected to fail at full app compile until this is done.
2. **MongoDB consistency:** The official driver, verified local replica set, installed indexes and selected actual no-charge MongoDB tier's transaction capabilities are **not** proven. Security-changing multi-document operations explicitly require a transaction and fail closed if the runner is unavailable. Synthetic rollback is not evidence about the real driver.
3. **Real OAuth:** No Google/GitHub OAuth client credentials, exact callback registrations, OIDC issuer/nonce/state/PKCE exchange, real provider identity linking or session-browser journeys were performed. Verification remains **BLOCKED** until an isolated configured local account completes both provider flows.
4. **Cookie/CSRF and host boundary:** No live browser evidence of `__Host-` cookie scope, direct host vs sibling-subdomain cookies, framework Server Action behavior, forged forwarded headers, actual OAuth callback URL enforcement or trusted edge behavior. Wildcard TLS and live production host selection remain blocked under Issue 19.
5. **Operator and security:** Privileged administrator bootstrap was tested only with synthetic approved operator state. Actual audited operator authorization, chosen credentials/rotation/retention, rate limits, dependency advisories, legal/privacy notices and release launch gates must be reviewed separately. Current `FEATURE_REGISTRATION` defaults to disabled; actual production feature enablement remains gated.
6. **Product functionality:** Full onboarding, portfolio creation, content schemas, editing, publication, media and public/AI data access belong to Issues 5–20 and are not enabled by this work. The dashboard is intentionally a minimal authorization demonstration, not a complete owner UI.

**Release decision: NO-GO.** This report is an implementation handoff with bounded, reproducible local evidence—not a claim that the integrated authentication system is production-ready. Provider-dependent and database-dependent acceptance tests `T-IAM-01`–`T-IAM-09` must remain **BLOCKED or PARTIAL**, not PASS, until tested through official installed libraries, an approved actual MongoDB instance and a real browser. The 18 deployment feasibility gates in Issue 1 have not been cleared.

# Issue 4 — Identity and authorization boundaries

**Authority:** GildedIn specifications 02, 05 §7, 06 §6/§10, 07 (identity/session/CSRF and threat model), 09, 10, 11 and ADR-004/010/029. **Status:** implementation candidate, not a release approval.

## Server-side trust graph

1. `src/auth.ts` delegates OAuth state, OIDC nonce, code/PKCE, issuer/signature checks and upstream authorization to the established **Auth.js** provider adapters. Its Google subject MUST match the verified `sub`; its GitHub subject is the verified numeric provider ID. Email is never an identity key, and a missing GitHub email is acceptable.
2. The successful Auth.js callback creates/resolves a stable account via `MongoAuthRepository` and writes its provider identity and restricted audit event in a single **real MongoDB transaction**. Provider subject is unique and race-safe. New registration defaults OFF. The short-lived, encrypted Auth.js session is **not** accepted for application authorization.
3. After redirect to `/login/complete`, the same-origin browser obtains a CSRF HMAC bound to the short Auth.js cookie. The `POST /api/v1/accounts/me/sessions/complete` handler verifies the real `auth()` result, exact apex origin, proof and bounded body before atomically recording a unique OAuth-exchange digest, a hashed application session and its audit event. This prevents replay of the handshake. On success it sets `__Host-gildedin_session` (host-only `Secure; HttpOnly; SameSite=Lax; Path=/`). It never sets `Domain`, uses URL bearer tokens or leaks upstream OAuth credentials.
4. Every `/api/v1/accounts/me/*` handler re-resolves the account from the database session, comparing the opaque bearer hash, persisted security generation, idle/absolute expiry and the still-linked login provider. `app/(owner)/dashboard` repeats server-side host/session checks. All private responses are `no-store`.
5. All authenticated mutations require exact `Origin`, allowed Fetch Metadata, a session-bound CSRF token and bounded JSON, **in addition to** server-side authorization on every repository write. Sibling subdomains have no CORS permission. The proxy is not an authorization decision.
6. Link-intent creation requires recent reauthentication (10 min), active session and CSRF, and sets a five-minute host-only HttpOnly linking cookie. `/login/link` revalidates the actor, linked provider and expiration before beginning a new, verified Auth.js flow. On callback, the same session, account and provider must match; identity insertion and audit are transactional, and security generation is bumped. No automatic email merging.
7. Unlink requires *recent authentication via the provider that will remain*, not merely the presence of two provider rows. A transaction compares the current account security generation, removes one identity and writes its audit event. Concurrent unlink of both providers cannot succeed.
8. Session sign-out and sign-out-everywhere revoke durable session state or the account security version; provider-link and unlink also revoke previous sessions. Read-time revocation is authoritative, not TTL timing.
9. `GET/PATCH /api/v1/accounts/me` permits only a safe projection and one editable field (`displayName`); verified contact email, provider ID, status, admin roles and timestamps are never client-editable. Accounts without a portfolio are a valid state.
10. Platform administrator bootstrap is **offline operator-only** (`scripts/bootstrap-admin.mjs`), requires deliberate operation-specific approval and a verified provider subject, and is denied from any HTTP route. It updates a server-owned role with transactional audit and revokes existing sessions. This is not self-registration or password/email-based account recovery.

## Required assumptions / limitations

- **Transactional durability is a precondition.** This issue's multi-record authorization, linking, unlinking and audit writes require verified MongoDB transactions. Without them, the repository refuses those operations. The synthetic transaction runner proves code-level ordering and rollback only, **not** actual MongoDB or Atlas Free behavior.
- **Provider verification is delegated, not reimplemented.** No homemade OIDC verification, homegrown OAuth callback exchange, custom password database or upstream access-token persistence is introduced. Auth.js v5 provider integration, Next.js Server Action behavior, OAuth callback URL registration, cookie delivery and genuine provider accounts are **not verified** in this environment.
- **Dependency prerequisites are unresolved.** This ZIP does not contain the official `mongodb` or `next-auth` packages or lockfile entries. They must be fetched from a reviewed registry on a connected machine and pinned/reconciled; otherwise the full app build correctly fails.
- **Host trust depends on the chosen edge.** The auth callback handler/Server Actions independently validate the canonical `Host`/`Origin` and reject conflicting forwarded headers. Actual proxy/TLS/cookie scope requires live local browser and deployment evidence, especially before wildcard is enabled.
- **Operator approval is not equivalent to a complete audited operations process.** Bootstrap requires a trusted authenticated maintenance environment, verified admin subject and reviewed operation ID. No HTTP admin role mutation has been enabled.
- **No rate-limit provider selection or deployment is approved.** Identity-specific rate-limit policy, OAuth client restrictions, live account proofs, audit retention policy, license approval and real browser cookies remain launch gates.

## Security regressions covered by synthetic tests

The local harness contains multiple independent synthetic tenants. It rejects repeated OAuth handshake proofs (including concurrent exchanges), expired and revoked sessions before TTL deletion, unknown and cross-tenant provider identities, forged Google/GitHub subjects, email collision merging, link-intent account/session/provider swapping, stale linking, concurrent two-provider unlink, missing CSRF, unsafe redirect candidates, mass assignment, unauthorized bootstrap and audit-write failures. A failed audit write restores synthetic writes atomically. **Browser/provider/real-Mongo equivalence is not claimed.**
